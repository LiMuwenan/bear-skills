# Conversation Archive

把对话里「将来还会用到」的信息沉淀成文件，而不是保存全部聊天记录。代码和测试是事实来源，本 skill 产出的是**解释来源**。

## 何时触发

- 用户明确要求：归档 / 记录 / 保存决策 / 总结这次会话 / 收尾
- 完成一个功能、修完一个复杂 bug、做完一次技术选型后，用户表示「结束了」「先到这」
- 对话中出现明显的需求变更、角色/术语定义、被放弃的方案，用户说「记一下」

不触发：纯问答、闲聊、一次性查询。

## 三种模式

根据用户措辞选择，不确定时默认 `snapshot`。

| 模式 | 触发场景 | 行为 |
| --- | --- | --- |
| `snapshot` | 对话结束 / 阶段性收尾 | 新建一份完整归档 |
| `append` | 对话进行中，说「记一下」 | 追加到当天已有归档或新建 |
| `promote` | 已有归档，要求提炼 | 把归档提炼成 ADR / issue 草稿 |

## 工作流

### 1. 确认输出位置

默认 `docs/agent-log/`。若项目已有 `docs/adr/`、`docs/decisions/`，先询问用户用哪个，不要擅自建第二套目录。

### 2. 创建文件

`snapshot` 模式运行本 skill 目录下的脚本：

```bash
bash scripts/new-archive.sh "<主题>" [slug]
```

脚本会创建 `docs/agent-log/YYYY-MM-DD-<slug>.md` 并打印路径。若同名文件已存在，脚本会提示改用 `append` 模式，不要覆盖。

`append` 模式：若当天已有同主题文件则在其末尾追加 `## 追加记录 YYYY-MM-DD HH:MM`；否则按 `snapshot` 新建。

### 3. 填充内容

按 `templates/session.md` 的结构填写。**只写对话中真实出现过的内容**，不要脑补、不要补全没讨论过的决策。信息缺失的章节写 `- 无` 或直接删除该章节。

提取时优先关注：

- **需求变更**：原需求 → 新需求 → 变更原因 → 影响范围
- **决策**：选了什么、为什么、放弃了什么、代价是什么
- **角色 / 术语**：项目中自定义的角色、模块代号、业务术语及其含义
- **约束**：技术、合规、性能、兼容性上的硬限制
- **废弃方案**：试过但放弃的方案，以及放弃原因（这是最容易被漏掉、也最有价值的部分）
- **待办与风险**：未完成项、已知坑、需要人工确认的点
- **人工修改点**：agent 生成后被人工改过的关键代码，注明原因

### 4. 脱敏检查（强制）

写入前逐项检查并移除：

- API key、token、密码、连接串、私钥
- 真实姓名、手机号、邮箱、身份证、地址
- 客户数据、未公开的业务数字
- 内部域名、内网 IP（如需保留，替换为 `<internal-host>`）

发现敏感信息时，用 `<REDACTED: 类型>` 占位，并在回复中提醒用户「已脱敏 N 处」。

### 5. 更新索引

在 `docs/agent-log/INDEX.md` 顶部表格追加一行，格式见 `templates/index-entry.md`。索引按日期倒序。

### 6. 回报

完成后用不超过 5 行回复：

```
已归档：docs/agent-log/2026-10-24-auth-refactor.md
模式：snapshot
记录：3 项决策 / 2 项需求变更 / 1 个废弃方案 / 4 项待办
脱敏：2 处
未覆盖：无
```

## promote 模式

用户要求把归档提炼成正式文档时：

- 架构类决策 → `docs/adr/NNNN-<title>.md`（沿用项目现有 ADR 编号规则）
- 待办 / 缺陷 → 生成 issue 草稿文本，不直接调用平台 API
- 术语表 → 合并进 `docs/glossary.md`（若存在）

提炼后原归档文件保留，在文件头加一行 `> 已提炼至：<路径>`。

## 硬性规则

1. 不覆盖已有归档文件，只追加或新建
2. 不把整段对话原样贴进文件，只保留结论 + 原因 + 关键片段
3. 代码片段只保留「能说明决策」的最小片段，完整代码引用 commit hash
4. 归档文件必须能独立读懂，不依赖对话上下文
5. 不确定的信息标注 `（待确认）`，不要编造
6. 单份归档控制在 300 行以内，超出则拆分主题
